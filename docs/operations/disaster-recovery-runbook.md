# Megalith Disaster Recovery & First Deployment Runbook

This document is the authoritative operational runbook for executing disaster recovery, recovering from interrupted operations, and performing the first real deployment of Megalith on an OCI Always Free Ampere A1 ARM64 virtual machine.

---

## 1. Architecture & Security Invariants

* **Single-VM Architecture**: Megalith runs entirely on a single OCI Ampere A1 VM (4 OCPUs, 24 GB RAM, Oracle Linux 9 / Ubuntu 22.04 LTS).
* **Network Isolation**: Only Caddy binds public host ports (80, 443). In production (`compose.yaml` + `compose.prod.yaml`), Caddy sits at static IP `172.28.0.10` on `edge-network`. Backend containers communicate across isolated bridge networks with zero host port exposure.
* **Header Trust**: `FORWARDED_ALLOW_IPS` is restricted to `127.0.0.1,172.28.0.10`. Spoofing headers from peer containers or outside the edge proxy is rejected.
* **Separation of Authorization**: Release manifests are immutable declarative data (Schema v2). Deployment authorization is an authenticated operator action tied to a canonical SHA-256 digest of the manifest. Self-declared approvals inside manifests cannot self-authorize.
* **Conservative Recovery**: The deployment engine never automatically drops tables or downgrades Alembic schema revisions. If a non-backward-compatible migration fails or is interrupted, the engine halts with `manual_intervention_required`.

## 2. First Live OCI Deployment Runbook

### Phase A: Infrastructure & Host Provisioning

1. **Terraform Apply (Admin Workstation)**:
   ```bash
   cd platform/infra/oci
   terraform init
   terraform plan -out=tfplan
   terraform apply tfplan
   ```
   *Provisions VCN, public subnet, security lists (ports 22, 80, 443), and the Ampere A1 Compute instance with `cloud-init.yaml.tftpl`.*

2. **Wait for Cloud-Init Completion**:
   SSH into the new instance:
   ```bash
   ssh opc@<OCI_INSTANCE_PUBLIC_IP>
   sudo journalctl -u cloud-init -f
   ```
   Ensure Docker daemon, Docker Compose v2, `age`, and non-root user `megalith` are provisioned.

3. **Configure Operator Environment & Secret Storage**:
   Populate production secrets at `/var/lib/megalith/production.env` with `0600` permissions owned by `megalith:megalith`:
   ```bash
   sudo mkdir -p /var/lib/megalith/releases /var/lib/megalith/backups /var/lib/megalith/keys
   sudo chown -R megalith:megalith /var/lib/megalith
   sudo chmod 700 /var/lib/megalith
   ```
   Generate the backup X25519 keypair:
   ```bash
   age-keygen -o /var/lib/megalith/keys/backup_key.txt
   chmod 600 /var/lib/megalith/keys/backup_key.txt
   ```
   *Record the public recipient key (`age1...`) and securely store the private key off-host in an encrypted password manager or KMS.*

### Phase B: Operational Preflight Checks

Run non-mutating preflight validation prior to any deployment:
```bash
python3 platform/deploy/scripts/preflight.py \
  --compose platform/deploy/compose.yaml \
  --compose platform/deploy/compose.prod.yaml \
  --state-dir /var/lib/megalith \
  --min-disk-gb 5 \
  --min-ram-mb 1024
```
Preflight validates:
* Host operating system and CPU architecture (`aarch64` / ARM64 or compatible).
* Docker daemon availability and Docker Compose v2.
* Host resource headroom (at least 5 GB free disk space on `/var/lib/megalith` and 1024 MB available RAM).
* Loopback port bindings (80, 443 available for Caddy).
* State and backup directory permissions (`0700` or `0750`).

### Phase C: Operator Deployment Authorization

1. **Inspect Signed Release Manifest**:
   Review `release.json` (Schema v2) generated by GitHub Actions CI for the target commit SHA:
   ```bash
   python3 platform/deploy/scripts/release.py validate /path/to/release.json
   ```
2. **Generate Deployment Authorization Record**:
   The operator signs the release on the host (or via secure deployment CLI):
   ```bash
   python3 platform/deploy/scripts/release.py authorize \
     --manifest /path/to/release.json \
     --operator "alice@megalith.internal" \
     --environment production \
     --output /var/lib/megalith/releases/auth-rel-001.json
   ```
   *This computes the canonical SHA-256 digest over the manifest's services, images, and migrations, recording the authenticated intent with `0600` permissions.*

### Phase D: Execute Controlled Deployment

```bash
python3 platform/deploy/scripts/deploy.py apply \
  /path/to/release.json \
  --auth /var/lib/megalith/releases/auth-rel-001.json
```
The deployer executes:
1. Acquires exclusive host lock (`/var/lib/megalith/deploy.lock`).
2. Validates authorization against manifest canonical digest and target environment.
3. Persists durable transaction state in `prepared` phase (`fsync` ensured).
4. Transitions to `migrating`: Runs `alembic upgrade head` via `demo-migrate`.
5. Transitions to `applying`: Launches containers via Compose with immutable digests.
6. Transitions to `verifying`: Validates container health and HTTP API readiness (`/ready`).
7. Transitions to `succeeded`: Marks release active in `/var/lib/megalith/state.json`.

## 3. Crash & Interrupted-Operation Recovery Runbook

### Scenario: Process Killed, Host Reboot, or Interrupted Deployment

If a deployment process terminates abruptly (SIGKILL, host crash, kernel panic) midway through an update:

1. **Inspect Host State**:
   ```bash
   python3 platform/deploy/scripts/deploy.py status
   ```
   Output will display the active interrupted transaction:
   ```json
   {
     "status": "failed",
     "active_transaction": {
       "tx_id": "tx-20261011120000-rel-002",
       "phase": "applying",
       "operator": "alice@megalith.internal",
       "updated_at": "2026-10-11T12:05:00Z"
     }
   }
   ```

2. **Execute Safe Recovery**:
   ```bash
   python3 platform/deploy/scripts/deploy.py recover
   ```
   The recovery engine:
   * Inspects the transaction's interrupted phase (`prepared`, `migrating`, `applying`, or `verifying`).
   * Queries the live PostgreSQL database for the current Alembic revision.
   * Compares the revision against target and previous release manifests.
   * If the interrupted phase is `prepared`: Aborts cleanly and resets transaction.
   * If interrupted during `migrating` or `applying`:
     * Checks if applied migrations are backward-compatible.
     * If backward-compatible: Restores previous release containers via Compose.
     * If non-backward-compatible: Halts and marks `manual_intervention_required` (never downgrades DB automatically).
   * Verifies health of rolled-back services.
   * Marks state as `rolled_back` and records audit entry.

## 4. Disaster Recovery: Restoring PostgreSQL from Encrypted Cold Storage

### Scenario: Complete Host Loss or Storage Corruption

If the VM or storage volume is completely destroyed:

1. **Provision New Host**: Follow Phase A above using Terraform.
2. **Retrieve Cold Backup Artifacts**:
   Download the latest backup pair from off-host storage (e.g., OCI Object Storage bucket):
   * `backup-db_demo-<timestamp>-<hash>.dump.age` (encrypted ciphertext)
   * `backup-db_demo-<timestamp>-<hash>.meta.json` (backup manifest)
3. **Verify Integrity**:
   Verify the SHA-256 checksum recorded in the `.meta.json` manifest:
   ```bash
   sha256sum backup-db_demo-*.dump.age
   # Compare against sha256_checksum in .meta.json
   ```

4. **Verify Decryption & Restore via Clean-Container Drill**:
   Before modifying production data, run an automated disaster-recovery restore drill in a freshly spawned, isolated container:
   ```bash
   python3 platform/deploy/postgres/restore.py clean-container-drill \
     --backup-file /var/lib/megalith/backups/backup-db_demo-*.dump.age \
     --identity /var/lib/megalith/keys/backup_key.txt
   ```
   This spawns a clean container, verifies database bootstrap DDL, decrypts and restores the schema without plaintext on disk, asserts Alembic revision and application data integrity, updates the manifest with verified_restorable: true, and unconditionally destroys the temporary container.

5. **Execute Full Production Restore**:
   If the drill succeeds, restore into the target production database:
   ```bash
   python3 platform/deploy/postgres/restore.py restore \
     --backup-file /var/lib/megalith/backups/backup-db_demo-*.dump.age \
     --identity-file /var/lib/megalith/keys/backup_key.txt \
     --database db_demo \
     --container megalith-postgres-1 \
     --clean
   ```
   *Note: `--clean` drops existing tables in `db_demo` and recreates them from the backup.*

6. **Verify Application Readiness**:
   ```bash
   curl -fsSL http://127.0.0.1:8000/ready
   # Returns: {"status": "ready", "service": "demo/api", "database": "connected"}
   ```

## 5. Automated Backup & Retention Management

Backups are executed daily via systemd timer (`megalith-backup.timer`):
* Service unit: `platform/deploy/postgres/systemd/megalith-backup.service`
* Timer unit: `platform/deploy/postgres/systemd/megalith-backup.timer`

### Safe Retention Policy
The retention engine (`prune_backups`) enforces fail-closed safeguards:
* Minimum 7 daily backups retained.
* Pruning is **strictly blocked** if the most recent backup failed, if off-host export failed, or if restore verification failed.
* The last known verified restorable backup is **never deleted**, regardless of age.
* Dry-run mode (`--dry-run`) is available for operator inspection.
